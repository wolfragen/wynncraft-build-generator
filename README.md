# Wynncraft Build Generator

Finds the best **crafted** item for a Wynncraft profession given a stat query.

You describe what you want — minimums, maximums and per-stat weights (e.g. "mana
regen is worth 1150× durability, defReq ≤ 115") — and the generator searches the
space of 6-ingredient crafts (recipe × ingredient placement) for the
highest-scoring legal build, then prints a wynnbuilder crafter URL.

> **New here?** See [`docs/`](docs/README.md) for the full developer
> documentation — architecture, per-subsystem references, data formats, and a
> glossary + gotchas list. This README is the short version + the authoritative
> soundness caveats below.

## How it works (short version)

A craft is a recipe + up to 6 ingredients placed in a 2×3 grid. Each ingredient's
stats are scaled by its slot **effectiveness**, which depends on neighbouring
ingredients' **posMods**. To make the search tractable the ingredients are split:

- **"Meta" ingredients** — those with posMods / `ingredEff` / charges / positive
  durability. Their arrangements (and the resulting per-slot effectiveness) are
  enumerated and Pareto-culled **offline** into `data/precalc/.../META_n.json`
  (`META_n` = `n` fixed meta ingredients + `6−n` void slots). Generated by
  `precalc_fast.py`, culled by `precalc_culling.py`.
- **"Normal" ingredients** — no posMods; they don't change anyone's
  effectiveness, so they're searched **at runtime** to fill the void slots via a
  numba branch-and-bound DFS (`core/search_engine.py`).

`main.py` wires it together: build a `Query`, load the recipe, filter+cull
ingredients into an `IngredientDB`, then `search_pipelined` overlaps meta-set
loading with the DFS.

Score = `Σ weight·(0.99·max_roll + 0.01·min_roll)` over stats + composites.

### `full_meta` (optional)

`build_query(..., full_meta=True)` runs an extra pass that recovers builds whose
**six** slots are all meta ingredients (see caveat #1). It extends each surviving
`META_5` row by dropping every meta ingredient into its void slot, recomputing the
whole grid, and compares the best complete build to the normal optimum (logging
time + count). Off by default.

## Running

```bash
# uses the conda "AI" env
python main.py
```

Edit the `user_query` / `skill` block in `main.py` to change the search.

## Regenerating the precalc

```bash
python precalc_fast.py       # enumerate raw meta-set arrangements
python precalc_culling.py    # Pareto-cull them into data/precalc/generic_cull/
```

## Known sub-optimality / soundness caveats

The search is **not guaranteed to return the globally optimal craft.** The choices
below can drop the true optimum. Each is tagged with how strongly it's confirmed.
Examples use the sample query in `main.py` (JEWELING ring, `mr` weight 1150,
`durability` weight 1, min 100, reqs capped).

### 1. The normal pipeline can't build all-meta (6-meta) crafts — *by design* **[PROVEN]**
`META_n` only goes to `n=5` (5 fixed meta ingredients + ≥1 void). A craft whose
six ingredients are **all** meta ingredients has no void slot and is unreachable.
*Verified:* the true optimum for the sample query — `Eye×2 + Lunar×4`, both Eyes at
200 % effectiveness, **16 mr** — is six posMod ingredients; the normal search tops
out at 13 mr (score 15145). The `full_meta` pass recovers it (score 18557).

### 2. `full_meta` only extends the *culled* META_5 survivors **[BY CONSTRUCTION]**
`full_meta` seeds from the Pareto-culled `META_5` rows, not the full enumeration.
A 6-meta optimum is missed if **every** one of its six 5-ingredient bases was
dropped by the `META_5` cull. *Why it can happen:* the cull scored each base with
its 6th slot empty; a base whose strength only appears once the 6th meta
ingredient's posMods reshape it can look dominated and be culled. Mutual-boost
pairs (P boosts Q, Q boosts P, both carrying weighted stats) are the failure
family — removing either collapses the other, so both bases can be dominated by a
simpler high-effectiveness arrangement. Not observed to bite on JEWELING, but
unproven in general. (Extending the *un-culled* 5-sets would be sound but costs
`6·m⁶` ≥ direct `m⁶` enumeration.)

### 3. Slots can't be left empty + the "useful mask" prunes harmless fills **[VERIFIED]**
`IngredientDB` has no "empty" sentinel and the DFS iterates only real ingredients,
so **every void slot is force-filled.** Compounding this, `_compute_useful_masks`
prunes any ingredient that can only *hurt* a slot at its effectiveness sign — which
is sound only if you may decline to fill the slot. Together they force a *worse*
fill than "nothing":
- *Verified:* the sample query's `META_5` base (`Eye,Bob's,Lunar,Eye,Lunar` + empty)
  is 13 mr / dura −504 → with recipe base ⇒ **~301 dura, score ≈ 15251**. Leaving
  the 6th slot empty would beat the normal best (15145).
- *Verified:* `useful_pos_eff[Fuming Lava Rock] = False`, so the least-harmful real
  fill (Fuming, −35 dura, score 15216) is pruned at the positive-eff slot, and the
  search picks Condensed Darkness instead (−106 dura, 15145) only because its
  `intReq −20` registers as "useful."

  (In the sample query the 16 mr `full_meta` build dominates all of these, so the
  *final* answer is still correct there — but for any query where no 6-meta build
  wins, this omission changes the result.)

### 4. The offline cull bakes "requirements are lower-is-better" **[CODE-CONFIRMED]**
`precalc_fast._filter_and_pack` / `_compare_recipes_jit` treat every `*Req` stat as
strictly lower-better (`is_req_global`). So the precomputed meta sets already
dropped high-requirement arrangements. A query that *wants* a requirement high
(e.g. `"defReq": {"weight": +100}`) can never see those builds — the optimum was
culled before runtime. (Matches the project note on positive-weighted-req queries.)

### 5. The runtime meta-row cull keeps a single representative per stat **[CODE-CONFIRMED]**
`data/meta_set_loader._build_cull_matrix` collapses each stat's `[min,max]` roll
range to **one** value (the user-preferred bound) before the dominance test, so it
can drop a row that's worse on the chosen bound but better on the other — which
still matters for constraints and for the `0.01·min` score term. Mitigated by only
running on small tiers (`suggested_max_cull = 3` ⇒ META_1..3; META_4/5 pass
through), but lossy in principle. The legacy `fast_cull=True` ingredient cull has
the same single-representative flaw under inversion and is documented unsound — it
is **off by default**; do not enable it for inversion queries.

### 6. Composite-stat B&B bounds assume monotonicity **[ASSUMPTION]**
Spell/EHP/EHPR upper bounds are corner evaluations that assume the formula is
monotone in its dependencies ("we rely on this… in practice", `search_engine.py`).
A composite that is non-monotone on the reachable region could get an inadmissible
bound and have a valid branch pruned. Holds for the current registry; revisit if a
non-monotone composite is added.

### 7. Score is a fixed 0.99/0.01 max·min blend **[MODELING CHOICE]**
"Optimal" is defined as the max of `Σ w·(0.99·max + 0.01·min)`. This is a heuristic
for "expect near-max rolls"; a different roll model (pure expected value, worst
case, etc.) would rank builds differently. Not a dropped candidate, but it defines
the objective the search optimises.
